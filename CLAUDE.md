## Build and run
- `dotnet build "Smart Tools.WPF/Smart Tools.WPF.csproj"` (use the csproj; the `.slnx` also holds the old `SmartToolsWPF.Setup` installer project the CLI can't build). A release folder is made with the `win-x64` publish profile (Visual Studio Publish, or `dotnet publish "Smart Tools.WPF/Smart Tools.WPF.csproj" -p:PublishProfile=win-x64`).
- If the app is running the exe is locked: `Get-Process -Name SmartTools | Stop-Process -Force` first.
- There is no automated UI test; verify by building, and say when something was not run in the app.

## Where things are
- `Shared/Controllers/ToolCatalogManager.cs` - the one list of categories and tools (id, name, icon, keywords). Sidebar, Home and search are built from it.
- `MainWindow.xaml.cs` - `Add<View>("tool-id", shutdownAction)` registers each view. **The id in the catalog, in `Add<>`, and in the
  `Str_Tool_<id>_Name/_Description` language keys must be identical**, or the tool silently won't open or will show an English fallback.
- `Tools/<Category>/<Tool>/` - `*View.xaml(.cs)` (UI only), `*Manager*.cs` (logic, no WPF types where possible; partials like `.Run.cs`), `*Model.cs` (data).
- `Language/en.xaml` + `es.xaml` - every UI string, tool names, guided tours. Always add to **both**. No English literals in views: XAML uses
  `{DynamicResource Str_...}`, C# uses `Loc.T(key, fallback)` / `Loc.F` / `Loc.N` (singular/plural) from `Modules/Loc.cs`, dialog titles use `Str_Tool_<id>_Name`.
  `FileDrop.Attach(view, onFile)` (`Modules/FileDrop.cs`) adds drag-and-drop of one file to a view.
- `Engines/` - bundled FFmpeg, VLC, Tesseract, Whisper. `Modules/` - app services (paths, settings, theme, language, log, toasts).

## Tests and ub-mode checks
- `dotnet test "Smart Tools.WPF.Tests"` (xUnit, 34 tests). It covers only the pure helpers that `Smart Tools.Shared/Smart Tools.Shared.csproj` compiles from the app's own source files (ByteFormat, NaturalStringComparer, SafeFileOps, AtomicFile, JsonSettings). To cover another pure file, add a `<Compile Include=... Link=...>` line there; the app does not reference that project.
- `.\tools\ub-check.ps1 dryer|crapper|mutator|all`: `dryer` = copied method bodies (`tools/dryer.py`, exact copies only), `crapper` = CRAP score per method from coverage (`tools/crapper.py`), `mutator` = Stryker.NET on Smart Tools.Shared (run `dotnet tool restore` first; config in `Smart Tools.WPF.Tests/stryker-config.json`; reports go to `artifacts/`, ignored by git). Crapper and mutator only see the linked helpers, not the views.

## Rules that have bitten before
- Tools never overwrite a user's file (`SafeFileOps.UniquePath`), write through temp-then-move (`AtomicFile`), and keep originals until the result is verified.
- A file or folder the user deletes/moves while a tool holds its path is skipped, never a crash, a hang or a retry loop: list folders with `SafeIo.EnumerateFiles/EnumerateDirectories` (empty + `onSkipped` callback when the folder vanished), read sizes with `SafeIo.TryGetLength`, treat `SafeIo.IsGone(ex)` in per-item catches as Skipped (Copy Queue does), and let the batch go on.
- Remember how a tool is set up, never which folders the user picked.
- Theme tokens only (`DynamicResource`), no hex colors in views; shared styles live in `Themes/Controls.xaml`.
- Keep WPF drawing off non-UI threads (STA), and keep clipboard calls in the view.
- Media seeking (`MediaViewerView`): never seek on every slider `ValueChanged` while playing. Pause on press, scrub throttled, one seek on release.
- Mini player: Minimize hides mini + app; first taskbar restore shows the mini, the next opens the tool (`MainWindow._restoreWidgetFirst`).
- Catalog ids starting with `future-` would show the shared "coming soon" page (`FutureIdeaView`); none exist now.
- `MediaElement` cannot open a file whose name has `#` or `%` even with a correct Uri (`new Uri(path)` is already right; do not escape it again). Media Viewer plays such files through a hard link/copy in `%TEMP%\Smart Tools\media-viewer previews` (`MediaViewerManager.MakeSafeAlias`). Video Replay still opens files the plain way.
- The options sidebar is dark in both themes: use `SidebarInputBg`/`SidebarText`, not `AccentColorSubtle` (nearly white in Light). Shared chip look: `PillChipStyle`.
- `media-viewer` is `MediaHubView` (pages: mixed, photos, videos, music). The mixed page is `MediaViewerView`; the Music page is `AudioReplayControl`. Spectrum bars: `SpectrumLevelMapper` (shared maths), `MediaSpectrumFeeder` (reads the file beside MediaElement), and the `SpectrumBars` control (namespace `Smart_Tools.WPF.Controls`, file `Tools/Media/MediaViewer/SpectrumBars.cs`).
- **Adorners are drawn above everything in the window, the modals included** (`AppModal.Show` overlay and `AppModal.Present` / `ModalLayer`). The data grids' rounded outline (`Controls/RoundCorners.cs`, an `Adorner`) crossed the dimmed page and the modal card until it was made to listen to `Views/ModalState` (raised by both modal paths) and hide while one is open. Any new adorner must do the same; prefer drawing inside the element's own tree.
- Icon names: the app uses MaterialDesignThemes 5.4.0. A wrong `PackIconKind` in `Kind="..."` only fails when the page opens (an `x:Static` fails at build, MC3011). Check new names against 5.4.0 (it renamed some, e.g. `Printer_3d`).
- Language files are UTF-8 with BOM; check for mojibake (`Ã¡`) after bulk edits. Keep `en.xaml` and `es.xaml` key sets identical (script check).

## Where we left off (updated 2026-11-25, NEW TOOL: ASCII Video Maker)
**UNCOMMITTED, built OK, 465 tests pass, keys en=es, 118 tools.** `ascii-video` "ASCII Video Maker" (es "Video ASCII", category art, `Tools/PixelSprites/AsciiVideo/`). Alan's use case: Bad Apple (3:39) as ASCII. Source = a link (yt-dlp from Web Audio Saver, at most 720p, one video, temp copy deleted after) or a video file (button or drop on the page). **How it works (fast, nothing frame-by-frame on disk):** FFmpeg decodes straight to ONE grey pixel per character cell (`scale=cols:rows:flags=area,format=gray`, raw on stdout) -> `AsciiVideoMath.FrameToChars` (ramp) -> `Compose` stamps pre-drawn Consolas glyph masks (GDI+, drawn once per run in `AsciiVideoManager.Masks`) into a grey frame -> piped into a second FFmpeg (libx264, + the original sound of the same stretch via `-map 1:a:0?`). Outputs: MP4 with sound, GIF (640 px, <=15 fps, 16-colour palette, from the MP4), and a text folder: `frames.txt` (header `ASCIIVIDEO 1 cols rows fps frames`, count written as 10 digits and filled in at the end, then every frame as `rows` lines), `sound.wav`, `play.ps1` (console player: sizes the window, plays the WAV, shows the frame for the elapsed time so it stays in sync, Esc stops) + `play.cmd` (runs it with `-ExecutionPolicy Bypass` for that run). Options: width 40-240 characters, 10/15/24/30 fps, ramps Smooth / Detailed (70 chars) / Blocks / Sharp, white on black or black on white, optional part, max 10 minutes. Never replaces (free names), a stop/failure deletes what the run made. An "own responsibility" disclaimer is always on the page (Alan asked for it). Rename note: the probe record is `AsciiVideoProbe` (Video Editor already has `VideoProbe`). **Verified:** unit tests (grid, ramps, compose, header, probe, command lines) + a real FFmpeg round trip in xUnit; the WHOLE pipeline through the app's own `AsciiVideoManager.ConvertAsync` from a scratch console harness (10 s, 480x360 black/white test video with a tone): 300 frames in 6.0 s (so Bad Apple ~2-3 min), MP4 1440x1092 h264 + aac 10.0 s, GIF, frames.txt 1+300*42 lines, sound.wav, play.ps1 parses in PS 5.1 and the frame join returns the right size; a frame from the MP4 looked right; a stop halfway left nothing. **NOT verified:** the page itself in the app (my UI Automation run hit the window while Alan was using the PC; stopped, nothing ran), a real YouTube download, the console player actually playing in a console window, Blocks ramp glyphs, Light/Glass, Spanish.
